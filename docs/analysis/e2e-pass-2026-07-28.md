## P0 — the run pipeline is broken for every test type

### P0-1 · Agent-relayed runs are instantly marked FAILED by the tester's stderr INFO stream
Evidence:
- Run `e3e99169` (full-stack rerun): `started_at → finished_at` = **10 ms** for a
  5-mode × 10-run benchmark; the agent journal shows it had only just logged
  `Spawning tester …` — no completion ever logged.
- ALL 4 runs' `error_message` is the tester's **startup INFO line**
  (`INFO networker_tester: Starting …`), not an error.
- Run `dfd05106`: `success_count=60, failure_count=0` — every probe succeeded —
  yet `status=failed`.
- The tester's tracing subscriber writes INFO to **stderr**; the agent streams
  stderr back as `error` frames (documented in `AnsiText.cs`). The control
  plane's agent-message processing appears to treat the FIRST error frame as
  run-fatal: marks the run failed+finished, stores the frame as
  `error_message`.
- Regression window: run `5f336e3a` (2026-07-19 18:00, agent v0.28.1) completed
  correctly WITH persisted attempts → the break landed between v0.28.2x and
  v0.28.96 while the fleet was drained (nothing exercised this path; the soak
  checks health, not E2E runs — see "process gap" below).

**Where to look:** control-plane processing of agent `error` frames
(AgentMessageProcessor / run-lifecycle handling; possibly a quality-wave
run-lifecycle change). Expected behavior: stderr frames are LOG relay, only the
run_finished frame (or a real fatal) decides status.

### P0-2 · Per-attempt probe rows never persisted (likely consequence of P0-1)
`GET /test-runs/{id}/attempts` → `[]` for all new runs even though
`success_count=60`. Run-detail pages are empty; reports/analytics get no probe
data. Probable mechanism: attempts arrive after the run was already forced
terminal and the persistence path drops them — verify while fixing P0-1
(if independent, fix separately).

## P1

- **P1-3 · No readiness gate between target provisioning and benchmark
  dispatch.** Deployment `auto-e2e-fullstack-nginx-70b74cac` reported
  `completed` at 21:03 (VM create returned), benchmark fired 21:05, stack was
  actually serving later (curl 200 at ~21:14). All 50 iterations failed
  instantly. Dispatch must poll the target's `/health` (the deploy pipeline
  already knows the URL — the tester was pointed at it) before assigning.
- **P1-4 · URL Probe probes `https://<host>/health`.** The Diag flow appended
  `/health` to `example.com` — arbitrary public sites 404 there, producing
  false "failed" verdicts. Probe should hit the URL as given (`/` for a bare
  host). Endpoint-kind default leaking into the URL flow (the #377–379 class).
- **P1-5 · Benchmark `failure_count` synthesized to the methodology count.**
  Both full-stack runs report `fail=50` (the "50 measured" plan) though nothing
  executed — claims 50 attempts happened. Counters must reflect actual
  attempts.

**P0-1 is fixed and verified live.** Statuses now match reality; the stderr
relay lands in the control-plane journal as INFO (which immediately produced
the next finding):

- **P1-14 (NEW) · Full-stack auto-provisioned target serves an invalid TLS
  cert: `CaUsedAsEndEntity`.** The tester (rustls) rejects every connection —
  all 50 attempts fail with `invalid peer certificate: Other(CaUsedAsEndEntity)`
  (`curl -k` masks it; the 60/60 network run's older target is fine). Either
  the target cert generation emits a CA cert as the server cert, or the
  benchmark path should pass `--insecure` for self-signed targets like the
  network path effectively tolerates. Fix in the P1 wave with P1-3.
- **P0-2 confirmed unchanged** (attempts still `[]`) — the missing
  `OnAttemptEvent` persistence port is the next P0 to fix.

### Teardown findings (deleting the E2E infra through the product)

- **P1-16 (NEW) · Deployment delete leaves the cloud VM orphaned.**
  `DELETE …/deployments/{id}` on the auto-provisioned target returned **200**
  but the Azure VM `nwk-auto-e2e-fu` + NIC/IP/NSG/disk/DevTestLab-schedule kept
  running — I had to delete them by hand via `az` to stop billing. Deployment
  delete removes the DB record but not the infra; the orphan reaper is
  tester-scoped, not deployment-scoped. Real cost leak.
- **P2-15 (NEW) · Non-force tester delete returns an opaque `400` (empty body)
  when the synchronous cloud-VM delete "fails".** The tester was
  `running`/`idle`/old (all delete preconditions satisfied); the plain DELETE
  400'd with no message, `?force=true` succeeded (202) — and the VM *did* get
  removed async, so the 400 was misleading as well as unhelpful. Surface the
  cloud-delete error and/or make delete async-with-retry instead of a bare 400
  that pushes the user to guess `force`.
- **Worked:** the force tester-delete DID tear the runner VM +
  all resources down cleanly (no orphan) — the tester delete path itself is
  sound once it proceeds.
